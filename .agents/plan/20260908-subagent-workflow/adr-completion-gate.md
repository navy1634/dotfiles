# ADR: サブエージェント完了と最終判定の証拠ゲート

## Background

サブエージェントの処理中に親セッションが次工程へ進んだり、部分出力やファイルの存在だけで完了を判定したりすると、未完了の実装を evaluator へ渡す可能性があります。実装担当者の自己申告だけで最終完了を扱うと、独立検証の役割も弱まります。

## Options Considered

### A. 経過時間またはファイル存在で完了を判定する

処理が止まったように見える時点や成果物の存在を、次工程へ進む条件とします。

### B. 実装担当者の完了報告だけで次工程と最終完了を判定する

実装担当者が完了と報告したら、evaluator の明示的な検証結果を待たずに完了扱いにします。

### C. 明示的な完了報告、検証証拠、evaluator の独立判定を順に要求する

依存工程はサブエージェントの完了報告と実装証拠を受けてから開始し、最終完了は acceptance evidence、DoD、evaluator の PASS、client の明示的な照合を揃えた場合だけ扱います。

## Rejected Because

- A は、部分出力や未完了のファイルを完了と誤認するため不採用です。
- B は、実装担当者が自分の成果物を独立検証なしに受け入れることになり、evaluator の役割を置き換えるため不採用です。

## Decision

C を採用します。サブエージェントを使う場合、次の依存工程へ進む前に、対象サブエージェントの明示的な完了報告と実装・検証証拠を受け取ります。実行中の対象への割り込み、再指示、編集は、具体的な阻害要因または明示的な依頼がある場合に限ります。経過時間、部分出力、ファイルの存在、親エージェントの推測、実装担当者の自己申告だけでは完了と判定しません。

## Rationale

工程の依存関係を明示的な報告で同期し、品質の判定を evaluator に分離すると、未完了作業の取り込みと自己承認を防げます。不要な介入を避けることで、サブエージェントの責務と実行結果も追跡しやすくなります。

## Impact

- orchestrate と workflow は、generator または他のサブエージェントの完了報告を受けるまで依存する次工程を開始しません。
- evaluator は、acceptance criteria、DoD、diff、全 ADR の明示的な証拠を確認して PASS / REVISE / REDESIGN を返します。
- client は evaluator の PASS と acceptance evidence の照合後にだけユーザーへ最終報告します。

## Unresolved Items or Review Conditions

- 並行して実行できる独立工程がある場合も、依存する工程の開始条件と完了報告を個別に記録する必要があります。
- 実行環境が構造化された完了イベントを提供するようになった場合は、明示的な証拠として扱えるイベントの形式を規約へ追加します。
